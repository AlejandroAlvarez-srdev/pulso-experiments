02 · A/B test: one-page checkout¶

Simulated data. Generated by pulso_exp.simulate (seed 42). The simulator plants a known effect, which lets the last section check the analysis against ground truth. Pulso is a fictional company.

Change under test: merchants creating an order go through checkout in three screens (quote → details → payment). Variant B merges details and payment into one page. Merchants are bucketed 50/50 by a hash of merchant_id (the way a feature-flag service would do it), so a merchant sees the same checkout for the whole test.

Outline: pre-registration → power & sample size → SRM → primary metric (z-test) → secondary metric with CUPED → guardrails → novelty → Bayesian read-out → why peeking is not allowed → ground-truth check → decision.

1 · Pre-registration¶

Written before looking at any experiment-period data (only the pre-period informs the numbers).

item choice
Hypothesis Merging details + payment removes a screen where merchants drop off, so more merchants who start a checkout end up placing a paid order.
Randomisation unit merchant (hash bucketing, 50/50). Sessions of one merchant are not independent, so the analysis unit is also the merchant.
Population (trigger) merchants with ≥ 1 checkout session during the 28-day window. Exposure is decided before the variant can matter, so triggering does not bias the comparison.
Primary metric merchant checkout conversion: share of triggered merchants with ≥ 1 paid order in the window. Two-sided two-proportion z-test, α = 0.05.
Secondary metric net GMV per triggered merchant (MXN, delivered orders). Welch t-test, with CUPED on pre-period GMV.
Guardrails p95 checkout page load (must not worsen > 5 %), payment failure rate among submitted payments, order cancellation rate.
MDE / power 3 % relative on the primary metric, 80 % power.
Duration 28 days = 4 full weeks (covers weekly cycles), fixed in advance. No early stopping.
Decision rule Ship if the primary metric is significantly positive and no guardrail is breached.

2 · Power analysis and sample size¶

The pre-period (same 28-day length, everyone on the old checkout) gives the baseline and the expected traffic.

def merchant_metrics(s: pd.DataFrame, o: pd.DataFrame) -> pd.DataFrame:
    """One row per merchant with >= 1 session in the given slice."""
    m = s.groupby("merchant_id").agg(
        sessions=("session_id", "size"),
        converted=("funnel_step", lambda x: (x == "paid").any()),
    )
    gmv = o[o["status"] == "DELIVERED"].groupby("merchant_id")["amount_cents"].sum() / 100
    m["gmv"] = gmv.reindex(m.index).fillna(0.0)
    return m

3 · Sample ratio mismatch (SRM)¶

Before reading any metric: did the split come out as designed? An SRM means the assignment or the logging is broken, and then no metric comparison can be trusted. The threshold is strict (p < 0.001) because the check runs on every test.

No SRM. The triggered split has p ≈ 0.03 — that would look "significant" at 0.05, which is exactly why SRM uses 0.001: with dozens of experiments a 0.05 threshold would raise false alarms every week. Since assignment itself is balanced and the trigger (opening checkout) happens before the new page is seen, this is chance, not a bug.

Raw-data duplicates would have mattered here: on the uncleaned session table, an ingestion retry that only hit one platform could create a fake session imbalance. Counting merchants (the randomisation unit), not sessions, avoids that.

5 · Secondary metric: GMV per merchant, with CUPED¶

CUPED (Controlled-experiment Using Pre-Experiment Data, Deng et al. 2013) subtracts the part of each merchant's metric that was predictable from before the experiment:

$$Y^{cuped}_i = Y_i - \theta\,(X_i - \bar X), \qquad \theta = \frac{\operatorname{cov}(Y, X)}{\operatorname{var}(X)}$$

X = the same merchant's pre-period GMV (0 if they were not active). Because X is measured before assignment it cannot be affected by the treatment, so the estimate stays unbiased; the variance shrinks by a factor of (1 − ρ²).

6 · Guardrails¶

A win on the primary metric does not ship if it breaks something else.

In [11]:
rng = np.random.default_rng(7)


def bootstrap_p95_diff(
    a: np.ndarray, b: np.ndarray, n_boot: int = 500
) -> tuple[float, float, float]:
    """Relative change in p95 (b vs a) with a percentile bootstrap CI."""
    point = np.percentile(b, 95) / np.percentile(a, 95) - 1
    boots = [
        np.percentile(rng.choice(b, b.size), 95) / np.percentile(rng.choice(a, a.size), 95) - 1
        for _ in range(n_boot)
    ]
    lo, hi = np.percentile(boots, [2.5, 97.5])
    return point, lo, hi

Cancellation rate is flagged: +15 % relative, p ≈ 0.03 at the unadjusted 5 % level. Before acting on it, two checks that should have been in the pre-registration:

  1. Multiplicity. Three guardrails were tested; with a Holm correction the smallest p-value must clear 0.05 / 2 (the latency guardrail is a threshold, not a test, so two tests remain).
  2. Clustering. Cancellations are order-level but merchants were randomised; a merchant-level (cluster) bootstrap gives the honest interval.

boot_rng = np.random.default_rng(11)


def cluster_rates(arm: str, n_boot: int = 2_000) -> np.ndarray:
    c, n = per_m.loc[arm, "sum"].to_numpy(), per_m.loc[arm, "size"].to_numpy()
    idx = boot_rng.integers(0, len(c), size=(n_boot, len(c)))
    return c[idx].sum(axis=1) / n[idx].sum(axis=1)

The result is genuinely borderline. After the Holm correction the cancellation p-value is ~0.06, just above 0.05. The cluster bootstrap barely moves the interval — merchants place only one or two orders each, so clustering is weak — and it still excludes zero. What tips the judgement is the mechanism: cancellations happen after payment, when no pulser can be found, and the checkout page plays no part at that point; the rate is higher at peak hours in both arms.

Here, and only here, ground truth is available: the simulator applies no treatment effect to cancellations, so this is a false alarm — three guardrails tested at 5 % make one of them flag fairly often. In a real launch we would not know that, so the flag goes into the decision as something to monitor, and the next pre-registration should state the guardrail multiplicity correction and the merchant-level estimator up front.

7 · Novelty effect¶

A new UI often gets a burst of curiosity that fades. If the lift shrinks over time, the full-window average overstates what we will keep after launch.

With this much data and a flat prior, the Bayesian and frequentist intervals almost coincide, as they should. The Bayesian framing adds two things stakeholders actually ask for: a direct probability that B is better, and the expected loss — how much conversion we expect to give up if we ship B and are wrong. Here that loss is negligible. What it does not give is a licence to peek: a posterior checked daily with a "stop when P > 95 %" rule also inflates error rates.

9 · Why peeking inflates false positives¶

"Check the dashboard every day and stop when p < 0.05" feels harmless. It isn't. Simulate 2,000 A/A tests (no true difference) with the same baseline and traffic as this experiment, and test after each of 28 daily looks:

Every look is another chance for noise to cross the line, and those chances add up. Most false wins come early, when samples are small — precisely when the temptation to stop is strongest.

Valid alternatives when early stopping is a business need: group-sequential designs with an alpha-spending function (O'Brien–Fleming), always-valid inference (mSPRT / confidence sequences), or a Bayesian decision rule on expected loss with a pre-agreed threshold. This test was pre-registered as fixed-horizon, so it was read once, on day 28.

For contrast, this is the real experiment's cumulative p-value. It crosses 0.05 early — partly real effect, partly the novelty bump — and a team stopping there would have reported an inflated lift.

10 · Ground-truth check (only possible because the data is simulated)¶

The simulator multiplies the details → payment submitted probability of treated sessions by 1 + true_uplift + novelty · 0.5^(day / half_life). Measuring that step directly should recover the planted value averaged over when sessions happened.

In [18]:
details = es[es["funnel_step"].isin(["details", "payment_submitted", "paid"])].assign(
    submitted=lambda x: x["funnel_step"].isin(["payment_submitted", "paid"])
)
dc, dt = (details[details["variant"] == v]["submitted"] for v in ("control", "treatment"))
step = two_proportion_ztest(int(dc.sum()), len(dc), int(dt.sum()), len(dt))
planted_avg = (
    uplift_multiplier(details.loc[details["variant"] == "treatment", "day"].to_numpy(), cfg) - 1
).mean()
print(
    f"details → payment, relative lift: estimated {step.relative:+.2%} "
    f"(95% CI [{step.ci_low / step.control:+.2%}, {step.ci_high / step.control:+.2%}]), planted average {planted_avg:+.2%}"
)
print(f"planted steady-state effect (after novelty): {cfg.true_uplift:+.2%}")

details → payment, relative lift: estimated +5.07% (95% CI [+3.60%, +6.54%]), planted average +5.78%
planted steady-state effect (after novelty): +4.00%

The estimate brackets the planted value, and the steady-state effect sits inside the interval of the late-window estimate from section 7. The merchant-level lift is smaller than the step-level one because a merchant with several sessions can convert even if one session fails — the effect gets diluted when it is aggregated to the unit we care about.

11 · Decision write-up¶

Recommendation: ship the one-page checkout, plan for a lasting lift smaller than the headline number, and keep a small holdout to watch cancellations.

question answer
Was the test valid? Yes: no SRM (assignment p = 0.26), arms balanced in the pre-period (notebook 01), fixed 28-day horizon read once.
Primary metric Merchant checkout conversion 51.9 % → 54.3 %, +2.35 pp, +4.5 % relative (95 % CI +2.5 % to +6.6 %), p ≈ 1e-5. Bayesian P(B > A) > 0.999, expected loss ≈ 0.
Secondary metric GMV per merchant +4.5 % with CUPED (95 % CI +2.8 to +36.9 MXN per merchant, p = 0.02); the raw estimate was inconclusive (p = 0.13). CUPED cut variance by ~16 %.
Guardrails Page-load p95 +1.8 % (limit +5 %); payment failures flat. Cancellations flagged (+15 %, p = 0.03; Holm-adjusted p = 0.06) with no mechanism linking them to checkout → monitor, not block.
How big is the lasting effect? Smaller than +4.5 %. The lift decays week over week; on days 15–28 the merchant-level lift is +2.3 % (95 % CI −0.4 % to +5.1 %). Plan on ~2–3 %, not 4.5 %.

Expected impact. At the pre-period baseline, a +2–3 % relative lift means roughly 1–1.5 more converting merchants per 100 who open checkout. Forecasts should use that range, not the full-window +4.5 %, which includes the novelty bump.

Follow-ups

  1. Roll out to 95 % and keep a 5 % holdout for 4 weeks to measure the post-novelty effect directly and to re-check the cancellation rate at the merchant level.
  2. Add the Holm correction for guardrails and a merchant-level (delta-method) estimator for ratio metrics to the pre-registration template.
  3. Find a stronger CUPED covariate for conversion (e.g. pre-period sessions, or a CUPAC-style model prediction): the binary pre-conversion indicator only removed ~3 % of the variance.

Ground truth check: the simulator planted +4 % lasting and +8 % decaying novelty on the details → payment step. The step-level estimate (+5.1 %, CI +3.6 % to +6.5 %) brackets the planted average (+5.8 %), and the late-window read correctly suggests a smaller lasting effect. None of the numbers here describe a real product.
